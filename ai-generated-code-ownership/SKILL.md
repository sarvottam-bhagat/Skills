# AI-Generated Code Ownership

## Overview

Use this skill when a codebase was substantially generated by an AI coding assistant and needs a human ownership pass before it ships or gets handed off. AI-generated code has a specific failure signature: it works, it passes the happy path, and almost nobody who "wrote" it can explain what a given function does or why a particular library was pulled in. That gap — code that runs but isn't understood — is where technical debt, security vulnerabilities, and painful handoffs come from. This is a review-and-cleanup practice, not a security or infrastructure checklist (see `backend-production-hardening` for that).

## Workflow

1. Identify how much of the codebase was AI-generated versus reviewed line-by-line, and whether anyone besides the original prompter can explain the key modules.
2. Audit against the checklist in `references/code-ownership-checklist.md`.
3. Prioritize the parts of the codebase that touch money, auth, or user data — read, rename, and understand those first.
4. Run a dependency and supply-chain pass: what's actually used, what's outdated, what's an unvetted community resource (prompt, skill file, copy-pasted config) rather than an audited package.
5. Leave behind documentation a future maintainer (including future-you) can use without re-deriving every decision from scratch.

## Audit Output

When asked to review or clean up AI-generated code, produce:

- **Comprehension read**: Which files/modules nobody on the team can currently explain in one sentence.
- **Dependency read**: Which packages are unused, outdated, or came from an unvetted source (a copy-pasted prompt, a community skill file, an unaudited script) rather than a normal package manager with a lock file.
- **High-impact fixes**: 5-8 ranked changes with expected impact and effort — renaming, deleting dead code, documenting decisions, pinning/auditing dependencies.
- **Handoff notes**: What a new engineer would need to run this locally, understand its architecture, and know what to do when it fails.

## Implementation Principles

- If you can't explain what a function does in one sentence, you don't own it yet. Read every file out loud (literally, or at least deliberately) before shipping — skimming is how a security hole or a silent bug survives review.
- Generic AI-given names (`processData`, `handleSubmit`, `fetchResults`) are a signal nobody has claimed the code yet. Renaming to what the code actually does is not cosmetic — it's the act of taking ownership, and it makes the next reader (often future-you) faster.
- Delete what isn't used. AI assistants generate extra helper functions, abstractions, and backup code paths nobody asked for. Unused imports, uncalled functions, and unrendered components are attack surface and maintenance burden with zero benefit — remove them rather than leaving them "just in case."
- Treat every installed dependency as code you didn't write but are now responsible for. Run an audit (`npm audit` or equivalent) regularly, commit the lock file, and know roughly what your transitive dependencies are — a package with hundreds of downloads is not the same thing as a security review.
- The supply chain now includes more than packages: prompts, downloaded "skill" files, shared configs, and community system-instructions that an AI assistant reads and acts on are also an attack surface, with no scanning tools or maintainer accountability behind them yet. Apply the same discipline — review before you feed it to an AI, isolate anything unvetted from production, and have a secrets-rotation plan ready if a resource turns out to be compromised.
- Documentation is not a nice-to-have added at the end — it's the difference between a project only one person (or one AI session) can run, and a product a team can actually own. At minimum: why each major architecture decision was made, how to set up the environment from scratch, and what to check first when something breaks.
